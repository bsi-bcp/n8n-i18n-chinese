# n8n 新版监控评估方案 —— 评审结论与 v2 实施

> 日期：2026-09-17 ｜ 评审对象：n8n 新稳定版自动监控+兼容性评估方案（v1）
> 结论：**总分 8.1/10 —— 方向正确、骨架可用；按 v1 原样实施会在 4 个已实证边界上翻车，已修订为 v2 并实施。**

## 一、背景与目标

需求：n8n 发布新稳定版时，自动触发评估，判断是否需要为 `bsi-bcp/n8n-i18n-chinese` 发布对应/兼容版本，并推送研发部群。

现有发布链（均已存在）：
- `node.js.yml`（原每小时 cron 盲跑）：查 n8n 新版 → LLM 翻译新 string → checkout n8n 源码打补丁构建 editor-ui → 自动打 tag `release/x.y.z` + GitHub Release（含 editor-ui tar.gz）
- `image.yml`（Release 事件触发）：构建 multi-arch 中文镜像推 `registry.bcpcloud.cn/bcp/bcphub-n8n/n8n-chinese:x.y.z`

断链现状：仓库缺 `GH_TOKEN`、`OPENAI_API_KEY`(+vars)、`BCP_REGISTRY_USERNAME/PASSWORD` 三组 secret/vars，两条链实际不可自动运行（2026-09-16 的 2.39.6 为人工发布）。

## 三、评审发现（逐条实证）

| # | 级别 | 发现 | 实证 | v2 修法 |
|---|---|---|---|---|
| D1 | 高 | `/releases/latest` 不可靠：n8n 仓库存在**非 prerelease 的移动 release「stable」**（published 比 n8n@2.39.6 晚 1s，draft:false）；且 2.x 与 1.123.x 双线并存，1.x 补丁可能成为"最新发布"误触发 | `GET /releases/tags/stable` + `releases?per_page=5` | 枚举 releases、正则 `^n8n@\d+\.\d+\.\d+$`、prerelease=false，只跟插件当前大版本线 |
| D2 | 高 | 老流水线以 `target_commitish`（`release/2.39.6`）作 checkout ref，但 n8n 仓库**当前已无此分支**（`git ls-remote --heads` 实证；9/12 发 2.38.7 时分支尚在，随后被上游清理） | ls-remote 输出 | 一律改用稳定存在的 git tag `n8n@X.Y.Z`；watcher 解析后经 dispatch input 显式传入 |
| D3 | 中 | 翻译缺口口径错：translate.js `collectMessages` 对**新增 key / 源文本变更 key / zh 缺失 key** 三类都重翻，v1 只数"新增"低估工作量 | translate.js L155+ | 评估器同口径：上游 en.json（pin 到 tag）vs `script/en.json` 快照 + `languages/zh-CN.json`，输出三计数+待翻译总数 |
| D4 | 中 | `git apply --check` 无 fuzz，上下文漂移即误报"不兼容"（假阴性） | git apply 行为 | 二级降级 `patch -p1 --dry-run --fuzz=3` 判🟡黄灯；门禁只看流水线实际应用的 `feat__i18n_zhCn.patch` |
| D5 | 中 | image.yml 构建失败完全静默（凭证缺失时每次都无声挂） | 无 failure 通知步 | 加 `if: failure()` 飞书卡片 |
| D6 | 低 | watcher cron 与手动可能重入双跑 | — | `concurrency: n8n-watch` |
| D7 | 低 | 阶段切换靠"secret 存在与否"隐式判断，不可控 | — | 显式 repo variable `AUTO_RELEASE`（默认 false）+ dispatch 参数 `report_only` |
| D8 | 低 | 演练卡片易被误读为真实事件 | — | force_version 演练带【演练】前缀、不入去重状态；验收含大线过滤负路径 |

附带发现（老流水线自身问题，v2 一并修复）：
- 翻译源 `N8N_EN_JSON_URL` 缺省用 **master**（可能领先所构建的 release tag）→ v2 固定 pin 到 `n8n@<版本>` tag
- `node --input-type=module translate.js` 参数无意义（translate.js 是 CJS）→ 移除
- image.yml `workflow_dispatch` 路径 checkout 的是 main 而非产物所在 tag → v2 dispatch 增加 version 入参并 checkout `refs/tags/release/x.y.z`
- Release 若由内置 GITHUB_TOKEN 创建，不会触发 `release` 事件 → image.yml 不接力（这就是需要 `GH_TOKEN` PAT 的原因，阶段 2 前置条件）

## 四、v2 实施内容

### 新增 `.github/workflows/n8n-stable-watch.yml`
- 触发：每小时 `:37` + 手动（`force_version` / `report_only`）
- 流程：D1 版本探测 → 已发布/已评估早退（cache 状态去重）→ checkout n8n **tag** → D4 补丁两级判定 → D3 三口径翻译缺口 → DockerHub 基础镜像 tag 检查 → 飞书评估卡片 → （AUTO_RELEASE=true 且绿灯/黄灯且镜像已出）自动触发 node.js.yml 并跟踪结果、失败建 issue（label `n8n-compat`）
- 阶段开关：`vars.AUTO_RELEASE`（默认 false）+ 手动 `report_only`；卡片附一键发版命令

### 修改 `.github/workflows/node.js.yml`
- 删除小时 cron（监控评估入口统一到 watcher）；保留 `workflow_dispatch`，新增 `version` 入参
- 版本解析：入参优先；兜底改为"枚举过滤后的最新稳定 tag"（不再是 target_commitish）
- n8n 源码 checkout ref 改 `n8n@<版本>`；翻译源 pin 到该 tag
- `permissions: contents: write` 显式化

### 修改 `.github/workflows/image.yml`
- `workflow_dispatch` 增加 `version` 入参；checkout 一律指向产物 tag `refs/tags/release/x.y.z`
- 新增失败飞书告警（D5）

### 实施过程踩坑记录（供后续维护）

1. YAML 步骤名含 `D4: xxx`（冒号+空格）→ 解析失败，GitHub 将文件名注册为名称且无触发器；已本地 PyYAML 前置校验
2. jq `def flat: reduce (paths(scalars)) as $p ({}; .[…]=getpath($p))` —— reduce 累加器覆盖 `.`，getpath 必须先 `. as $in` 捕获输入
3. jq object value 内管道必须加括号；`$var[$expr]` 索引后缀在 1.7/1.8 解析报错，改用 `has()`/`. as $e` 绑定
4. jq 1.7+ 字符串转义收紧，正则 `\.` 改 `[.]` 免转义
5. bash `set -e` 陷阱：`VAR="$([ cond ] && echo x)"` 在条件为假时整条赋值非零退出；改 if 赋值
6. runner 上未认证 GitHub API 调用会被共享 IP 限流 → 一律带 GITHUB_TOKEN
7. GitHub Actions workflow 解析失败时 dispatch 报 422 "does not have workflow_dispatch"，name 显示为文件路径 —— 这是 YAML 语法错误的信号

## 七、风险与备注

- Actions cache 7 天不用会被清理 → 状态丢失时会重复评估一次同一版本（卡片重复一条，可接受）
- `git apply --check` 在 shallow checkout 上执行，与流水线构建环境一致，误报率低；黄灯建议人工看一眼 fuzz 后的补丁内容
- 1.x LTS 线如需跟进（例如生产还跑 1.x），把 watcher 的 `OUR_MAJOR` 改为白名单数组即可，当前默认不跟
