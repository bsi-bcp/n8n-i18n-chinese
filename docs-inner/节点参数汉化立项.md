# 节点参数汉化项目章程（立项）

> 立项日期：2026-09-19 ｜ 发起：用户 ｜ 状态：**M0 POC 已完成并通过用户出口确认（2026-09-19：YTJ1 实机 Code 节点参数面板全中文，后端 types payload 注入路径实证）→ 待启动 M1 全量提取**
> 背景：节点参数面板（一切节点的 displayName/options/description/hint/placeholder）为最后一块未汉化面。审计结论（见评审记录「节点参数汉化统一审计」）：参数串硬编码于 nodes-base 源码、经后端 types payload 直出、**前端渲染时不过 i18n 查表**——Code 节点 Mode/选项全英文即此因。量级估算：500+ 节点 × 每节点数十参数串 ≈ **数千至上万条独立字符串**。

## 目标

节点参数面板全量简体中文：参数名、选项、描述、占位符、提示。质量标准沿用既有体系（术语表统一 + LLM 量产 + 人工评审 + 覆盖率门禁）。

## 技术路线（关键决策点）

### D-P1 渲染注入方式（M0 核心调研，二选一或混合）
| 方案 | 原理 | 优劣 |
|---|---|---|
| A 前端构建补丁 | 改参数渲染组件（ParameterInputList 等）过 i18n 查表 | 查表精确；🔴 上游每次重构需跟维护 |
| B 构建后 dist 后处理 | 同 brand-patch/语义脚本哲学：对构建产物做参数串→中文的定向替换 | 免维护渲染层；🟡 minified 串匹配需谨慎（避免误伤标识符） |
| C 上游参数 i18n 化 | 推动或等待 n8n 官方支持节点参数 i18n | 根治；🔴 不可控时间表 |

**倾向**：B 为主（复用已验证的 brand-patch/语义脚本基建），A 视 B 的效果决定。

### D-P2 键方案
参数串无稳定键（与 UI 壳不同）。候选：`节点类型 + 参数 path + 选项 value` 组合键，或「英文原文 → 中文」直接映射表（推荐——与上游解耦，上游改结构不影响映射表；风险=同文多义需按节点上下文分译）。

### D-P3 提取器
新增 `extract-node-parameters.cjs`：从 n8n 源码（nodes-base `*.node.ts` 的 properties 定义）或运行实例 `/types/nodes.json` 提取全量参数串 → 产出待翻译清单（去重、按节点分组、标注上下文供 LLM 翻译质量）。

## 风险与对策

| 风险 | 对策 |
|---|---|
| 上游 minor 重构致提取/映射失效（预研实证的半衰期问题在参数级放大） | 提取器每次发版重跑；映射表按英文原文锚定（结构无关） |
| 万级 LLM 翻译的语义质量 | 术语表强约束 + 人工抽样评审 + 客户反馈回路 |
| minified 替换误伤（标识符/非显示串） | 只替换带显示语境的模式（如 `displayName:"X"` / `name:"X"` 引号包裹形态）；替换后构建校验 |
| 方案 B 对新上游版本的一次性适配 | 每版构建日志报告命中率，命中率骤降即告警 |
